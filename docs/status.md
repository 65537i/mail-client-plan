- MIME深度境界をmailparse 0.18.0で測定。product cap 30に対し、同一single-child multipart入力のdepth 31と100をparseしてtreeを返し、101で内蔵再帰制限エラーとなる。内蔵値は100でAPIから変更できず、parse後の深度検査は解析時CPU/stack/allocationの上限にならない。`message/rfc822`はtree上leafであり、追加再帰parseではbudgetを別途伝播する必要がある。[ADR-002](./adr/ADR-002-imap-candidate-poc.md)
- `message/rfc822`再parseでもcaller-owned depth budgetの必要性を確認。PoC側の上限30を各再parse前に適用すると30階層を完了し、31階層目のparseを始めず拒否できる。これは合成連鎖での呼び出し規約確認で、mailparse APIや製品adapterのresource guaranteeではない。
- Decoded-output limitの実測: 34 MiB raw UTF-8本文（50 MiB raw cap内）の各byteを不正`0xff`にすると、mailparse `get_body()`は各byteを3-byte U+FFFDへ置換し102 MiB Stringを返す。これは100 MiB decoded capを越える。返却後の長さ検査では超過allocationを防げず、候補APIにbudget付きdecodeはない。
- Part-count amplification: 20,000個の1-byte text partを含む1 MiB未満のmultipartをmailparseが全part treeとしてparse・保持し、part数指定やallocation budget APIはない。raw input上限だけではpart-node数を直接制限せず、parse後検査はnode allocation後となる。[ADR-002](./adr/ADR-002-imap-candidate-poc.md)

quoted-printable診断境界（00C / AC-04前提）: 合成入力で`=GG`は本文に保持され、末尾単独`=`と不完全な末尾`=A`は本文から脱落し、`=\rX`はCRを失って`=X`として残る。小文字`=3d`と大文字`=3D`はどちらも`=`へdecodeされ、通常CRLFは本文に保たれるが、hard line末尾のspace / tabは除去される。76 / 77文字のASCII行は両方とも長さ検証なしに受理され、単独CRは本文から消えて隣接文字を連結する。末尾改行のないbodyでは、`=20` / `=09`およびliteral space / tabがEOFまで保持される。multipart boundary直前のhard lineではliteral space / tabは除去される一方、encoded `=20` / `=09`は空白として本文に残る。混在hard line endingでは、最初のCRLF後に続くbare LFもCRLFとして本文に出力される。裸LF soft breakの後続hard CRLFはCRLFとして保持され、soft breakのLFはhard line styleを変えない。multipart part末尾の通常CRLFはboundaryで除かれるが、`before=\r\n--boundary`ではopening / closingいずれのdelimiter直前でも本文が`befo`へ切り詰められ、末尾`re` 2 bytesが無診断で失われる。`=`後のspace / tabがあっても同じ損失となる。LF delimiterでは`before=\n--boundary`と`before= \n--boundary` / `before=\t\n--boundary`の全てで本文は`befor`となり末尾`e` 1 byteが失われる。いずれも後続partとraw sourceは保たれ、`is_encoding_problem=false` / MIME診断default。一方、`before=\r\ncontinued\r\n--boundary`のようにsoft break後に本文データが続けば`beforecontinued`を保持する。1〜4文字bodyではdebug buildの1文字形がdecoder内overflowでpanic、2〜4文字形が本文を2文字短縮。release buildではpanicなしだが1文字形にboundary hyphenが混入し、2〜4文字形は同じく2文字短縮。soft breakでは正規`=\r\n`、裸LFのみ、`=`後のspace / tab後CRLFの計4形がいずれも改行を落として本文を連結する。裸LF / whitespace形は規格準拠肯定例ではなく、parser toleranceとして記録。silent lossとprofile依存のpanic / corruptionを候補parser採用blockerとして扱う。`cargo test -j 1 -p mail-client --features mime-poc --test mime_candidate --locked --quiet`はdebug buildで59 tests成功。isolated release profileのquoted-printable 11 testsも成功。全quoted-printable異常系、解析中の資源制限、3OS runtimeは未確認。テスト追加とADR記録のみで製品コード・依存・CI変更なし。

本文文字コード診断の限界（00C / AC-04前提）: 合成fixtureで正当にUTF-8表現されたU+FFFD、およびASCII suffix前に不正Shift_JIS / EUC-JP / ISO-2022-JP sequenceを挿入した本文を比較。mail-parser 0.11.9はsequenceをU+FFFDへ変換してsuffixを保持するが、`replacement_character_present=true`、`unrecognized_text_charset=false`、`is_encoding_problem=false`を返す。UTF-16LEとUTF-16BEの双方で不正odd trailing byteを黙って落として本文を切り詰め、replacement診断はfalseのまま。両endianのunpaired surrogateはU+FFFDへ変換されるがencoding problemにはならない。原EMLは保たれるものの、診断から損失・不正sequence位置を特定できない。`cargo test -j 1 -p mail-client --features mime-poc --test mime_candidate --locked --quiet`は43 tests成功。テスト追加とADR記録のみで製品コード・依存・CI変更なし。他charsetの網羅、解析中のCPU / peak memory制限、fuzz、3OS runtimeは未確認。

追加境界確認: delimiter直前soft breakではLFが末尾1 byte、CRLFが2 bytesを無診断で失う。`=`後のspace / tabでも同じで、closing boundaryやEOF直結でも変わらない。ASCII 1〜4文字ではLFは1文字短縮、CRLFは1文字時にdebug overflow panic、2〜4文字で2文字短縮。UTF-8本文をraw bytesで置いた30形と`=XX` octet表現4種の24形では、soft break後がboundaryのとき改行形式に応じ本文が脱落 / U+FFFDへ破損。soft break直後に本文データが続く対照では、2-byte `=C3=A9`のoctet境界split（0 / 3 / 6）は`étail`として復元し、escape内部split（1 / 2 / 4 / 5）はIncomplete。3-byte `=E6=97=A5`の60形と4-byte `=F0=9F=98=80`の78形も、octet境界splitは各文字+`tail`を復元し、escape内部位置はIncomplete。隣接2文字列`=C3=A9=E6=97=A5`の114形でも、octet token境界splitは`é日tail`、escape内部splitはIncomplete。連続2 / 3 soft breakを挟む12形ではCRLF / LF・space / tabいずれも`étail`を保持。全形でpanicなし。CRLF short-bodyのisolated release検証は同version Tokio / mail-parserが別target instanceとして扱われる型不一致でcompileに失敗し、未確認。MIME candidateはLinux debug 72 tests成功。unit 5 + integration 72 = 77 tests。添付のnative Run 70（commit `82bf4a9`）はUbuntuのLinux依存パッケージ導入中にcancelされ、Rust / MIME test stepへ到達していない。現行mainのRun 72成功証跡とは別のrunであり、このPoCの3OS検証根拠にはしない。
